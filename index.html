A decent laptop or PC
Minimum: 16GB RAM, 256GB SSD, Intel i5 or AMD Ryzen 5. You need RAM to run multiple VMs simultaneously. 05
Scripted Attack Loop + High-Volume Triage
attacker VM loop / 50+ alerts/tickets / false-positive tuning / 30-second first look
Scripted LoopHigh-Volume Triage50+ TicketsFalse Positives
View Day 5 GitHub Log
▶
Now that tools exist, use them like a real SOC queue. Build a safe scripted attack loop in a lab VM, let the alerts stack up, then practice sorting noisy alerts quickly, deciding what deserves more time, tuning false positives, and writing tickets another analyst could act on.
1
Build the scripted attack loop
Run a Kali attacker VM on a timed loop, plus Windows/admin activity scripts, to create 50+ mixed alerts: failed logins, benign admin activity, suspicious PowerShell, file deletion, network scans, DNS/web noise, and new services. The current documented run used VirtualBox; the next run will repeat the workflow in VMware.
2
Flood Elastic/Wazuh, then work the queue
Let the loop run for 30-60 minutes, then triage the alert queue in batches. For each alert, make a first-look decision within 30 seconds: close as benign, mark false positive, investigate for 10 more minutes, or escalate with evidence.
3
Write and tune like an analyst
Track alert name, severity, affected host or user, timestamps, query used, verdict, next action, and tuning recommendation for recurring false positives.
PHASE GOALAt least 50 triaged alerts/tickets, 10 false positives tuned or explained, 5 escalations written, and average first-look triage time tracked.

SOC Operations Simulation
Intermediate Alert Queue Practice

Phase 5 is built around analyst-style queue work: a scripted lab attack loop generates repeated activity, Elastic/Wazuh collect the alerts, and each session is used to review evidence, tune noise, write case notes, and decide what needs escalation.

50+
Alerts Reviewed

30-60m
Lab Attack Loop
Timed Kali and Windows activity window to create realistic alert pressure.
10+
Tuning Decisions
Document recurring noise, suppression logic, or why an alert should stay active.
5+
Escalation Notes
Write L2-ready summaries with affected user, host, evidence, timeline, and next action.
30s
First-Look Triage
Initial analyst decision: close, tune, investigate deeper, or escalate with evidence.
How the volume gets created
An attacker VM and Windows/admin activity loop generate failed logons, PowerShell events, DNS/web noise, scans, new services, file activity, and identity changes.
How the loop runs
The Kali attacker VM runs timed scripts for 30-60 minutes, creating repeated but safe events that land in Elastic and Wazuh for triage practice. The documented run used VirtualBox; VMware repeat testing is planned.
What gets documented
Each session produces tickets, case notes, false-positive decisions, escalation summaries, and a short lesson learned for the build logs.

sudo systemctl status elasticsearch

sudo grep -i "error\|exception\|fatal\|failed" /var/log/elasticsearch/elasticsearch.log | tail -n 50

sudo chown root:elasticsearch /etc/elasticsearch/service_tokens
sudo chmod 660 /etc/elasticsearch/service_tokens
sudo chown -R root:elasticsearch /etc/elasticsearch
sudo find /etc/elasticsearch -type d -exec chmod 750 {} \;
sudo find /etc/elasticsearch -type f -exec chmod 660 {} \;

sudo systemctl restart elasticsearch
sudo systemctl restart kibana

Triage Method Used
  • For every event, I documented: event, user, command/process, parent, decision, and reason.
  • Expanded checklist: what triggered, who ran it, what process ran, what parent launched it, whether it was expected, whether it was suspicious by technique, whether context made it benign, and whether it should be closed, investigated, tuned, or escalated.
  • Important fields reviewed: winlog.event_data.User, CommandLine, Image, ParentImage, ParentCommandLine, event.code, and winlog.channel.
  • Learned the difference between human user context like DESKTOP-3JKM5O9\mmajeed and system/service context like NT AUTHORITY\SYSTEM.
  • Learned that the child process tells what ran, while the parent process tells where it came from.
Completed Triage Examples
  • net localgroup administrators - local admin group discovery. Verdict: benign by context, suspicious by technique.
  • PowerShell whoami - user context discovery from PowerShell. Verdict: benign by context, investigate if unexpected.
  • nslookup github.com - DNS lookup activity. Verdict: benign by context, review domain reputation in production.
  • curl.exe to github.com - command-line web request. Verdict: benign by context, suspicious if paired with download/execution.
  • HTTPS network connection on 443 - outbound network connection. Verdict: benign/tune if known process, investigate if unknown process or destination.
  • Windows 4624 Logon Type 5 - service logon. Verdict: close as benign unless unusual account or surrounding activity appears.
  • PowerShell parent process - PowerShell launching child processes. Verdict: review child command, parent, user, and timing before closing.
  • SYSTEM/services.exe activity - normal Windows service behavior unless paired with suspicious service creation or binary path.
  • calc.exe and notepad.exe - benign GUI launches in this lab, suspicious only if spawned by unusual parents.
  • ipconfig and hostname - discovery commands. Verdict: benign by context, suspicious if unexpected after compromise.
False Positive + Benign Decisions
  • PowerShell whoami, net user, and net localgroup administrators were expected from the lab loop.
  • curl.exe to GitHub/example.com and nslookup to Google/GitHub/Microsoft were expected connectivity and DNS tests.
  • notepad.exe, calc.exe, OneDrive HTTPS traffic, Windows service logon type 5, and SYSTEM/service activity were documented as benign in context.
  • The key lesson was not to close everything blindly: each item still needs user, process, parent, destination, timing, and surrounding-event context.
Escalation Notes Practiced
  • PowerShell user discovery: whoami from PowerShell can indicate post-compromise discovery if unexpected.
  • Local administrator group enumeration: net localgroup administrators can reveal privileged accounts.
  • Command-line web request: curl.exe can be used for payload download or external infrastructure testing.
  • HTTPS network connection: port 443 is common, but the process and destination determine risk.
  • Successful service logon: 4624 Logon Type 5 is usually service activity but still matters during access investigations.

  • Scripted Phase 5 loop generated high-volume endpoint telemetry for SOC triage practice.
  • Reviewed Sysmon Event IDs 1, 3, and 22 plus Windows Security Event ID 4624.
  • No confirmed malicious activity was identified in the lab environment.

Lessons Learned
  • Same event type can have different risk depending on user, parent, command line, destination, and timing.
  • Context is everything: whoami, curl, and net are not automatically malicious.
  • SOC analysts do not escalate everything; they decide what is benign, noisy, tunable, suspicious, or escalation-worthy.
  • Parent-child process relationships matter because a benign-looking child process can become suspicious with an unusual parent.
  • Troubleshooting the SIEM itself is part of the work. If Elasticsearch or Kibana breaks, investigations stop until the service issue is fixed.

Phishing Investigation, IOC Extraction, Email Triage, and Incident Reporting
✓ Phase 7 Complete 5 Phishing Cases IOC Extraction Incident Report
▶
Phase 7 Overview
  • Practiced one of the most common SOC L1 queues: user-reported suspicious emails and email security alerts.
  • Reviewed sender identity, display name, sender domain, reply-to, return-path, URLs, attachments, social engineering language, and authentication results.
  • Built a repeatable phishing workflow: review evidence, identify the attack goal, extract IOCs, decide the verdict, recommend SOC actions, and write the ticket.
Cases Investigated
  • Microsoft 365 password expiration: confirmed credential harvesting using a lookalike Microsoft domain and urgent account-suspension language.
  • Invoice ZIP attachment: suspicious invoice-themed email with possible malware delivery through a compressed attachment.
  • CEO / executive impersonation: BEC-style email with no link or attachment, proving phishing can be conversation-based.
  • Fake Okta security alert: MFA/security-alert themed credential phishing using urgency and account-lockout pressure.
  • Fake DocuSign document review: document-signing impersonation using a lookalike domain and fake secure review link.
Skills Practiced
  • Extracted sender emails, sender domains, URLs, root domains, attachment filenames, subjects, impersonated brands, and phishing themes as IOCs.
  • Separated verdict types: benign, spam, suspicious, phishing, malware delivery, credential harvesting, and BEC.
  • Recommended actions such as block sender/domain/URL, search for other recipients, quarantine matching emails, ask whether users clicked or entered credentials, reset passwords, revoke sessions, and review identity sign-in logs.
  • Wrote a final phishing incident report with executive summary, scope, key findings, IOC list, impact assessment, recommended SOC actions, and final verdict.
Lessons Learned
  • Display names can lie; the real sender address, domain, reply-to, and return-path matter more.
  • HTTPS does not make a link safe; analysts still need to inspect the root domain and context.
  • Phishing does not always include a link or attachment. BEC can start with a simple reply request.
  • ZIP files, lookalike domains, urgency, fear, executive pressure, and brand impersonation are major triage clues.
